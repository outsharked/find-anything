# Scoped, Named, Revocable Access Tokens (with Invite Enrollment)

Implements GitHub issue outsharked/find-anything#86.

## Overview

`find-server` authenticates with one static shared string
(`ServerAppSettings.token`), checked in `check_auth()` against the
`Authorization: Bearer` header or the `find_session` cookie. Every client
shares it, so there is no revocation, no identity in logs, and no scoping (a
read-only search client holds the same credential as one that can
`DELETE /api/v1/admin/source` or trigger `update/apply`).

This plan replaces that with:

1. **Scoped tokens** — `read` ⊂ `update-index` ⊂ `admin` (hierarchical).
2. **Named, optionally-expiring, revocable tokens** stored server-side (hashed).
3. **Invite enrollment** — an admin mints a short-lived, single-use invite code
   with `find-admin`; a new client redeems it for a strong token. No token is
   ever hand-copied between machines.
4. **The `token` in `server.toml` remains as the root admin credential**
   (already generated by `install-server.sh`). It is config-defined, always
   `admin` scope, and cannot be revoked through the API.

This supersedes only the "API keys" part of `070-security-model.md`. User
accounts, roles and per-source access control from that plan are out of scope.

## Design Decisions

### Scopes

`admin` ⊇ `update-index` ⊇ `read`. A route requires a minimum scope.

| Scope | Routes |
|---|---|
| `read` (default for anything unlisted) | `GET /sources`, `/file`, `/files`, `/search`, `/context`, `POST /context-batch`, `/settings`, `/metrics`, `/stats` (+`/stream`), `/errors`, `/recent` (+`/stream`), `/tree` (+`/expand`), `/raw` (+`/{source}/{*path}`), `/view`, `POST /links` |
| `update-index` | `POST /upload`, `PATCH /upload/{id}`, `HEAD /upload/{id}`, `POST /bulk` (writes to `data_dir/inbox/`) |
| `admin` | everything under `/api/v1/admin/*`, plus new token/invite management |
| none | `GET /links/{code}` (public, rate-limited), `check_link_code_auth`, `POST /auth/redeem`, `/auth/session` |

Wrong scope → **403**. Missing/invalid/expired/revoked token → **401**.

### Token model

- 256-bit random value, base64url, prefixed (`fa_`) so leaked tokens are
  greppable.
- Stored as **SHA-256 hash** only (sufficient because the token has full
  entropy; no bcrypt/argon2 needed). Shown to the caller exactly once.
- Fields: `id`, `name` (unique), `scope`, `token_hash`, `created_at`,
  `expires_at` (nullable), `last_used_at` (nullable, refreshed at most once per
  minute per token to avoid write amplification). Revoking a token **deletes
  its row** (so the name becomes reusable and there is no stale state to
  reason about); revocation is recorded in the server log.
- Storage: `data_dir/tokens.db` (SQLite, same pattern as `links.db`). This is
  not a source DB, so the "all DB writes through the inbox worker" invariant
  is unaffected.
- Lookup: hash the presented value, `SELECT` by hash, check not revoked / not
  expired. Small in-memory cache (hash → resolved principal, short TTL) so
  auth doesn't hit SQLite on every request; revoke invalidates the cache.

### Root admin token

`server.toml` `token` keeps its name and meaning-with-a-twist: it is the
bootstrap admin credential and is compared in constant time. Empty token
retains its current meaning (no auth at all — public demo instances). Nothing
about existing deployments breaks; clients using it keep working until an
admin issues scoped tokens and rotates them in.

### Invites

- `find-admin invite create --name <label> --scope <scope> [--ttl 15m]
  [--expires-in <dur>]` → `POST /api/v1/admin/invites`. Prints the code plus
  the exact redeem command. `--ttl` is the invite lifetime (default 15 m);
  `--expires-in` is the optional lifetime of the *resulting token*.
- **Scope and name are fixed by the admin at invite creation**, never by the
  redeemer.
- Code: 8 chars, Crockford base32 (no `I L O U`), displayed as `XXXX-XXXX`,
  case-insensitive on entry. ~40 bits, made safe by: single use, 15 min TTL,
  and rate limiting.
- `POST /api/v1/auth/redeem {code}` (unauthenticated) → validates the invite,
  atomically marks it consumed, creates the token, returns
  `{ token, name, scope, expires_at }`, and sets the HttpOnly `find_session`
  cookie for browsers.
- **Rate limiting**: per-IP limiter reusing the `link_rate_limiter` pattern;
  additionally a global cap on failed redeems per minute so a distributed
  guess can't outrun the 15 min window. Failed and successful redeems are
  logged with the token name.
- Invites live in `tokens.db` (`invites` table: `code_hash`, `name`, `scope`,
  `token_expires_in`, `expires_at`, `consumed_at`). Codes are stored hashed.
- Admin can list pending invites and revoke one
  (`find-admin invite list|revoke`).

### Management CLI / API

`find-admin` gains:
- `invite create|list|revoke`
- `token list` (name, scope, created, expires, last used, revoked)
- `token revoke <name>`

Backed by admin-scope endpoints: `POST/GET/DELETE /api/v1/admin/invites`,
`GET /api/v1/admin/tokens`, `DELETE /api/v1/admin/tokens/{name}`.
Revocation takes effect immediately (cache invalidated); no restart.

### Enforcement

Keep the per-handler pattern (narrowest diff, lowest risk):
`check_auth(&state, &headers)` becomes
`check_scope(&state, &headers, Scope::X) -> Result<Principal, StatusCode>`.
`Principal { name, scope }` is returned so handlers can log the caller's name
(satisfies the "identity in logs" goal). Existing `check_auth` call sites
(~40 across 14 route files) are swapped mechanically; a compile-time-visible
scope argument at every call site makes omissions easy to review.

Bearer header and cookie both resolve through the same lookup; the cookie
holds whichever token authenticated the session, so scope follows the
originating token.

### Session route fix

`create_session` currently writes `state.config.server.token` into the cookie
when the token comes via the Authorization header. It must write the
**presented** token instead. It validates via the same resolver.

### Delegation (find-upload → find-scan)

`upload.rs` passes `state.config.server.token` to the spawned `find-scan`,
which POSTs to `/api/v1/bulk` on `127.0.0.1`. The server instead generates a
random **internal `update-index` token at startup, held only in memory**
(`AppState.internal_token`), and passes that. It never appears in config,
`tokens.db`, or `token list`, and cannot be revoked by mistake.

### Clients

- **Web UI**: on 401 the login prompt asks for an **invite code** (raw-token
  paste still accepted for the root admin token). Redeem → store in
  `localStorage` (existing `find_token` key; `sessionStorage` would force a
  fresh invite per tab) and rely on the HttpOnly cookie for `<img src>`.
- **Headless clients** (`find-scan`, `find-watch`, `find-upload`,
  `find-anything`): `find-admin redeem <code> [--url <url>]` exchanges an
  invite for a token and writes it into `client.toml` (creating the file if it
  does not exist). It lives in `find-admin` rather than `find-scan` because
  `find-scan` takes a positional path argument that would clash with a
  subcommand. No protocol change on the wire: still `Authorization: Bearer`.
- **Installers**: `install.sh` and `packaging/windows/find-anything.iss` prompt
  for an invite code instead of a bearer token (raw token still accepted).
  Both must change together and keep identical option blocks.
- `install-server.sh`: message updated to explain invites; still prints the
  admin token once.

## Implementation

1. `crates/common`: `Scope` enum (ordered), token/invite API types; add
   `MIN_CLIENT_VERSION` consideration (see Breaking Changes).
2. `crates/server/src/db/tokens.rs`: schema, create/lookup/revoke/list,
   invite create/consume (single transaction so consume is atomic), hashing.
3. `crates/server/src/routes/mod.rs`: `check_scope`, `Principal`, resolver
   with cache, constant-time compare for root token.
4. Swap every `check_auth` call site for `check_scope` with the correct scope
   (table above); anything not clearly listed defaults to `read`.
5. `routes/session.rs`: use presented token; `routes/auth.rs` (new): redeem
   endpoint + rate limiter; `routes/admin.rs`: invite/token endpoints.
6. `upload.rs`: internal ephemeral token.
7. `find-admin` subcommands; client-side `redeem` helper + `find-scan redeem`.
8. Web: invite-code login flow, `api.ts` redeem call, `token.ts` unchanged.
9. Installers + docs (`docs/CLI.md`, `docs/manual/01-installation.md`,
   `README.md`), `docs/ARCHITECTURE.md` auth section, `CLAUDE.md` invariants,
   `CHANGELOG.md`.

## Testing

Server integration tests in `crates/server/tests/auth_tokens.rs` using
`TestServer`, plus updates to `helpers/mod.rs` if needed (root token
unchanged, so most existing tests should pass as-is):

- wrong scope → 403 (per scope tier, including one route from each of
  read/update-index/admin); no/bad token → 401
- expired token rejected; revoked token rejected immediately (cache check)
- cookie session inherits the originating token's scope; session created via
  header stores the presented token, not the root token
- invite: redeem success; second redeem fails (single use); expired invite
  fails; wrong code fails; scope/name come from the invite; token expiry
  propagates; rate limit returns 429; concurrent double-redeem yields exactly
  one token
- token list never exposes token values or hashes
- upload delegation still indexes with a non-admin-configured server (internal
  token works, is not listed)
- empty root token still means open access

CLI end-to-end: `find-admin invite create` → `find-admin redeem` → scan
succeeds with `update-index` token; same token gets 403 on an admin call.

Web: Vitest for the invite-code/raw-token login decision logic.

## Breaking Changes

- Existing root-token deployments keep working unchanged; **no forced
  migration**.
- New endpoints and 403 responses are additive for clients using the root
  token. A client with a *scoped* token hitting an out-of-scope route gets 403;
  old clients can't have scoped tokens, so `MIN_CLIENT_VERSION` only needs a
  bump if we change existing request/response shapes (we don't plan to).
- Operational follow-up (homelab, not in this repo): mint scoped
  `update-index` invites for synology1 and MUSIC3, redeem them, and remove the
  root token from those clients' configs. MUSIC3's `client.toml` should also
  be `chmod 600`.
